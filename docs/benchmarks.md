# Benchmarks

All numbers on this page were measured on the machine described below, with the code in this repository. Nothing is
estimated or extrapolated. Raw output is in [`benchmark-results/`](../benchmark-results).

## Environment

| | |
|---|---|
| CPU | Intel Core i7-13620H (10 cores / 16 threads), laptop |
| RAM | 15.7 GB total; 1.9-2.3 GB free during the reported run (0.7-0.9 GB during earlier runs) |
| Power | **On battery** (Windows reported `BatteryStatus=1`, discharging) during the reported run |
| OS | Windows 11 Home 10.0.26200 |
| .NET | SDK 10.0.401, runtime 10.0, Release build, workstation non-concurrent GC (benchmark project setting) |
| Host load | Shared machine: another agent building in parallel, browsers, sync clients. CPU load from other processes sampled between steps is in `benchmark-results/host-load.txt` (3-57 %) |

This is a noisy host. An earlier throughput run of nearly the same code (before the XName cache) is kept in
`benchmark-results/baseline/`: its medians are 1.5-2x lower than the reported run for the same rows, and a third run,
started while the host was busy, was 5-6x slower and was aborted. The round-robin method below was introduced
because of that. Treat absolute numbers as what a busy, battery-powered laptop achieves; the ratios between modes and
the memory figures (allocation is deterministic) are the robust results.

## Method

Invoices are generated by `tools/UblTr.SampleGen` (`SyntheticData.RandomInvoice(seed = lines, lines)`, with line tax
breakdowns, mixed VAT rates, allowances, 4-decimal prices). Every benchmark invoice is first validated and must have
zero findings.

Four modes isolate where the time goes:

| Mode | What runs |
|---|---|
| `parse-only` | `XmlReader` (DTD prohibited) into `XDocument` with line info. The floor for any tree-based design |
| `xsd-only` | parse + XSD validation against GIB's compiled schema set (`ValidationOptions.SkipRules`) |
| `rules-only` | parse + the 49 business rules, no XSD (`SkipSchema`) |
| `full` | parse + XSD + rules: what the CLI, API and Action do |

**Throughput** (`dotnet run -c Release --project benchmarks/UblTr.Benchmarks -- throughput`): all 24 (size, mode)
pairs are warmed up, then measured in 600 ms slices (at least one document per slice), round-robin in a shuffled
order for 7 rounds, so a load spike on the host hits a slice, not a whole row. The table gives the **median** slice,
and the slowest and fastest slice. Single thread. Allocation per document is `GC.GetAllocatedBytesForCurrentThread`
over the slice divided by documents.

**Peak memory** (`-- peak <file>`): a fresh process loads the schemas, validates one file once and reports its peak
working set; three processes per size, median reported.

**Scaling** (`-- scaling`): 100-line invoices, N threads validating in parallel with one shared validator, 7 rounds of
1.5 s, median.

**Micro** (`-- micro`): BenchmarkDotNet 0.15.8 default job for 10- and 100-line invoices, plus the XName lookup
comparison that motivated caching names in the rules.

## Results

Run of 2026-11-11, 20:40-21:10 local time. Host CPU load sampled between steps: 3 % before and after throughput,
10-13 % during scaling and peak, 50 % at the end of the micro step; free RAM 1.9-2.3 GB; laptop on battery throughout.
Schema set (19 GIB XSD files) compile time at start-up: 124 ms.

Per megabyte, full validation costs 20 ms/MB for small invoices (1-10 lines), 27 ms/MB at 1 000 lines and 50 ms/MB at
50 000 lines; parsing alone is 10-22 ms/MB. Over the 1-1 000-line range the work splits roughly evenly: at 1 000 lines
parsing takes 11.3 ms, XSD validation adds about 5.5 ms and the 49 rules add about 6.5 ms (25.3 ms in total). The
slowest slices are 5-20x below the medians: that is the host, not the code (see Environment).

### Memory

| Lines | File | Allocated per validation | Peak working set of a fresh process (median of 3) | Baseline (schemas loaded, before validating) |
|---:|---:|---:|---:|---:|
| 1 | 5.6 KB | 0.1 MB | 49.2 MB | 45.9 MB |
| 100 | 99 KB | 1.1 MB | 49.2 MB | 45.9 MB |
| 1 000 | 945 KB | 10.3 MB | 53.5 MB | 45.9 MB |
| 10 000 | 9.2 MB | 102 MB | 151.7 MB | 46.2 MB |
| 50 000 | 46.0 MB | 510 MB | 545.2 MB | 45.9 MB |

Allocation is about 11x the document size at every size, and the peak working set grows by about 10.8x the file size
above a 46 MB baseline (500 MB for a 46 MB, 50 000-line invoice). That is the price of the tree ([ADR 0003](adr/0003-single-pass-validation-into-xdocument.md)).
With the API defaults (20 MB body limit, concurrency = processor count) the worst case is bounded at roughly
220 MB per concurrent validation.

### Parallel scaling (100-line invoices, one shared validator, interleaved rounds)

| Threads | Docs/s (median) | Speed-up |
|---:|---:|---:|
| 1 | 608 | 1.00x |
| 2 | 942 | 1.55x |
| 4 | 1 275 | 2.10x |
| 8 | 1 136 | 1.87x |

The shared compiled schema set does not serialise validations, but scaling flattens beyond 4 threads on this
battery-powered laptop with a busy host. A first scaling run with non-interleaved rounds was discarded because load
changes landed on whole rows (1-thread rounds ranged 37-140 docs/s); its output was replaced by this run.

|---|---:|---:|---:|---:|
| Full | 10 | 242.9 us | 239.9 us | 187.4 KB |
| XsdOnly | 10 | 298.9 us | 305.8 us | 169.2 KB |
| RulesOnly | 10 | 242.6 us | 244.0 us | 159.8 KB |
| Full | 100 | 2 370.7 us | 2 485.4 us | 1 119.2 KB |
| XsdOnly | 100 | 1 353.3 us | 1 325.9 us | 988.2 KB |
| RulesOnly | 100 | 1 184.4 us | 1 123.4 us | 946.3 KB |

These ran last, while host load had risen to 50 %; the 10-line rows are inconsistent (XsdOnly slower than Full)
and should be read as noise-affected. The allocation column is deterministic and matches the harness.

XName lookup on an invoice line, which is why the rules use pre-built `XName` instances (`Rules/N.cs`):

| Method | Mean | Allocated |
|---|---:|---:|
| `line.Element(Ns.Cbc + "LineExtensionAmount")` | 26.2 ns | 0 |
| `line.Element(cachedName)` | 1.7 ns | 0 |

A shorter earlier run measured 17.0 ns vs 6.8 ns. Either way the saving is tens of nanoseconds per lookup, a few
milliseconds per 1 000-line invoice: worth having in a hot loop, but not visible above the host noise in the
end-to-end table.

### Not measured

- HTTP API throughput under load (only correctness under 24 concurrent requests is tested).
- Linux or container performance; all numbers are from the Windows host above.

## Reproduce

```bash
dotnet build -c Release
dotnet run -c Release --project benchmarks/UblTr.Benchmarks -- throughput benchmark-results
dotnet run -c Release --project benchmarks/UblTr.Benchmarks -- scaling benchmark-results
dotnet run --project tools/UblTr.SampleGen -- large /tmp/large 1,100,1000,10000,50000
dotnet run -c Release --project benchmarks/UblTr.Benchmarks -- peak /tmp/large/invoice-50000-lines.xml
dotnet run -c Release --project benchmarks/UblTr.Benchmarks -- micro --filter '*ValidationBenchmarks*' '*XNameLookup*'
```
